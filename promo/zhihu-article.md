# 我给"验证器"分了六级：为什么 AI 说"我检查过了"最不可信

> 副标题：LLM 验证领域的 L0–L5 分级，和一个被全行业忽视的"完备性盲区"
>
> 论文：Grading the Graders: Verification Autonomy Levels (L0–L5) for LLM Reasoning
> 代码与全文：https://github.com/1549080929-debug/math_agent

---

## 开场：AI 评审编了一条不存在的"证据"

前几天，我拿论文初稿给一个 AI 评审看。它洋洋洒洒写了几千字，其中一条"硬伤"振振有词：

> "PDF 中有明显的 LaTeX 渲染失败：`mathrm P x Rightarrow mathrm X subseteq mathrm C...`"

我当场把 PDF 提取出来逐页查——公式 `∀ c ∈ C : P(c)` 渲染得清清楚楚，全文 15 页里根本没有 "mathrm" 这几个字符。**那条"证据"是它自己编的，而且它不知道自己在编。**

最讽刺的是：这恰好是我论文要论证的现象——**AI 在没有地面真值锚定时，会自信地编造，还编得特别像回事。** 而我是用确定性检查（提取 PDF 文本）把它击穿的。

这不是段子，是方法论的一次现场演示。它引出我接下来要讲的整套框架。

## 一、LLM 需要验证器，但"验证"这个词已经乱了

大模型会流畅地、自信地、经常性地答错。主流解法是给它们挂"验证器"——步骤检查器、自一致性过滤器、工具增强的事实核查、形式化证明助手……2023 到 2025 年，这类论文多到数不过来。

但你翻开这些论文会发现：**"level（层级）"这个词，被至少五种不同的概念占用**：

| 他们说"层级"指 | 回答的问题 | 典型例子 |
|---|---|---|
| 粒度层级 | 拆多细去查？ | claim→句子→文档 |
| 概念层级 | 在什么抽象层面验？ | 基础元素→高级概念 |
| 风险/处置层级 | 验完怎么办？ | 安全/有条件安全/需关注 |
| 系统栈层级 | 审计哪一层？ | 模型→工作流→系统 |
| **锚定层级** | **凭什么判定？真值从哪来？** | **（本文）** |

前四种各有各的用处，但**没有一种回答最关键的问题：这个验证器的判定，到底锚定在什么地面真值上？**

## 二、VAL：验证的 L0–L5 自动驾驶分级

我借用了自动驾驶的分级思路——核心变量不是"能力"，而是**责任在谁**：

| 等级 | 判定依据 | 保证 | 自动驾驶类比 |
|---|---|---|---|
| **L0** | LLM 自己说"我检查过了" | 无 | 全手动（司机会自信地开错） |
| **L1** | 从题面提取的确定性规则 | 确定性匹配 | 车道保持 |
| **L2** | 客观真值/标准答案/金标 | 正确性 | 部分自动化（人必须随时接管） |
| **L3** | 可判定系统（符号求解/类型系统） | **单性质完备** | 有条件自动化（ODD 内系统负责） |
| **L4** | 领域级证明系统（证明内核） | 领域完备 | 高度自动化 |
| **L5** | 通用完备验证 | 任意性质 | **不可判定**（Rice 定理，不存在） |

判级只需回答三个问题：**验证条件谁声明的？保证的是"正确"还是"没有遗漏"？完备性覆盖多大范围？**——我把这套判级程序写成了可运行的代码（`val_standard.py`），任何人跑一遍都能得到同样的等级。

关键洞察：**层级由"锚"决定，不由"裁判"决定。** 一个校准精良的验证器，如果只是代回检查候选答案，它就是 L2——它永远发现不了"没被提出的候选"。把采样加密一万倍，也跨不进 L3；只有把问题重编码进可判定系统（比如用符号求解器做解集等价），才算抬级。

## 三、完备性盲区：正确 ≠ 没有遗漏

这是整个框架最核心的一个点，三句话：

1. **"提出的候选都成立"（正确性）≠ "没有候选被遗漏"（完备性）**——两者逻辑上完全独立；
2. 最常见的验证方式——代回、抽样、统计阈值——只能证明前者，永远无法证明后者；
3. 我管这叫**完备性盲区**，它不是 tuning 不到位，是验证范式的固有属性。

实证案例（数学）：系统求"所有解"，给出了 `a=2`。代回验证：PASS。但真解是 `{0, 2}`——漏掉的 `a=0` 对代回验证来说**根本不存在的**，它没有被问过。换成符号求解器做解集等价后，`"2"` 对 `{2,3}` 直接判 FAIL。同一个问题，L2 是盲的，L3 是可判定的。

最有力的一句证据来自文献里最强的形式化验证工作（Safe, ACL 2025）——它用 Lean 4 形式化验证每一步推理，但作者自己写：**"our formal verifier focuses on the correctness of each step"**（我们的验证器只关注每一步的正确性）。连最强的验证也只保正确性、不保完备性——完备性被推到了 LLM 声明的定理陈述层，没消失，只是往上挪了一层。

顺便：为什么不可能有"通用完备验证器"？Rice 定理——任意程序性质的通用判定不可判定。所以 L5 不是"还没造出来"，是**原则上不存在**。完备性只能在特定领域（ODD）内拿到，这决定了工程问题的正确问法永远是"哪个领域"，而不是"能不能"。

## 四、三个领域的实证：诚实的负结果

我用三章实验验证了这套框架，每一章都按"审计先行→测价值窗口→失败分类"的协议走：

**数学（第一章）**：给 LLM+SymPy 架构建了 42 个裁判用例，全过。但 20 题测试集跑了三轮：**16/15/13，而裸 LLM baseline 是 20/20**。准确率不升反降。我如实报告——架构的价值不在"更准"，在**错误可报告性**：把静默错误变成带标签的错误（比如当场抓住 `[-1,1]` 并修正为 `[0,1]`）。

**行为观测（第二章）**：统计检测器五轮迭代，FPR 从 92% 压到 30%、强攻击 TPR 1.0。但"隐匿执行"攻击（模型心里执行命令但输出不留痕迹）怎么都只能到 0.60——这是 L2 的结构性天花板，不是调参问题。

**医疗诊断（第三章）**：LLM 教科书病例 10/10、硬病例 8/10，失败模式清一色是"信息不足仍下结论"。我写了个信息完整性裁判（一条确定性的后置规则），**3/3 全部命中，零误报——还抓到了一个人类标注都漏掉的失败案例（#105）**。裁判的价值不只是复核，是发现。

三个领域一个规律：**LLM 太强，准确率窗口全空；非空的窗口全是"验证窗口"**——错误可报告性、ODD 内的检测、过度自信的拦截。

## 五、这对你意味着什么

- **如果你在部署 LLM 应用**：先问一句"验证条件是谁声明的"。如果答案是"模型自己说它检查过了"（L0）——恭喜你，你得到的是个装饰品。L2 的判定是"正确性探针"，不是"完备性保证"，文档里必须写清楚。
- **如果你在做 LLM 研究**：警惕把"粒度更细"说成"验证更强"——那是两个正交的轴。五轴混淆的现状，让大量"分层验证"论文互相蹭可信度。
- **如果你是审稿人**：这套框架给你一套问句——"这个验证是什么等级？ODD 是什么？超出 ODD 时它怎么弃权？"

## 结尾

大模型时代的验证，最缺的不是更聪明的裁判，是**知道裁判到底能保证什么**。

我给验证器分级，不是想分个高低贵贱——是想让"verified"这个词，在每个人嘴里恢复它本来的分量：**要么诚实地说"我只验了正确的部分"，要么证明"没有遗漏"；最不能接受的，是明明什么都没验，却说"我检查过了"。**

> 别人给答案分级，我们给"分级"分级。
> 而一个验证器能获得的最高分，是它能真正交付的保证：域内的正确性、ODD 内的完备性、以及它必须弃权时的诚实。
